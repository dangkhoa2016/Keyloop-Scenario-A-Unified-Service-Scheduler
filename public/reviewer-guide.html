Reviewer Testing Guide

10-minute guided walkthrough · realistic synthetic records · independently verifiable evidence

Before you start

Browse customers, vehicles, available slots and existing appointments without login. To confirm or cancel an appointment on the public demo, use the private Demo write token supplied by the author. Do not publish the token. Dates and times use Asia/Ho_Chi_Minh (UTC+07:00). Choose a future Monday–Saturday.

Step-by-step scenarios

  1. 1. Explore rich data. Switch among all six dealership locations, 20 customers and their vehicles. Expect the vehicle selector to update when customer changes.
  2. 2. Check full-duration availability. Choose North Service Hub → Oil Change → a future weekday. Observe start times. Change to Brake Inspection (90 minutes) and compare slots. Both technician and bay must cover the complete interval.
  3. 3. Compare schedule capacity. Try other dealerships or service types. Lunch shifts run 12:00–13:00; dealership opening hours are 08:00–18:00, Monday–Saturday. Exact free slots depend on existing bookings.
  4. 4. Inspect persistent appointments. Scroll to Appointments. Review confirmed and cancelled records. Every confirmed row contains technician and bay identifiers.
  5. 5. Confirm a booking (authorized reviewers). Enter the private token on the main page, choose a free slot and click Confirm appointment. Expect a confirmation containing an appointment ID, technician ID and bay ID.
  6. 6. Verify persistence. Refresh the page and find the same appointment. Its status remains confirmed.
  7. 7. Cancel and release capacity. Cancel only the appointment you created. The row remains with status cancelled, and capacity becomes reusable.
  8. 8. Inspect backend evidence. Run npm test and npm run test:concurrency locally. The second test starts 10 independent workers simultaneously; exactly one booking succeeds for the same constrained resources.

Architecture and review scope

The fully implemented service layer is Node.js + Hono + SQLite3. The UI uses Vue 3 and Tailwind CDN without a frontend build tool. The atomic booking transaction rechecks eligibility and uses database triggers to reject resource overlaps. Seed data and customer identities are synthetic. This Quick Tunnel is temporary, and manual accessibility verification is separate from automated browser tests.
